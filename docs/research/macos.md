## PART A: the code

### A.1 Everything that is Windows-only today

**Already abstracted (read): `app/src-tauri/src/platform.rs` (139 lines).** Its header says the backend "must also compile on macOS/Linux" and that every OS-specific thing lives there (platform.rs:1-6). It covers exactly five things:

| What | Where | Windows | Non-Windows |
|---|---|---|---|
| No console window / idle priority for child processes | platform.rs:11-41 | `creation_flags(0x0800_0000)` CREATE_NO_WINDOW, and `0x40 \| 0x0800_0000` IDLE_PRIORITY_CLASS (platform.rs:21-31) | no-op, returns `self` (platform.rs:33-41) |
| Home dir | platform.rs:44-49 | `USERPROFILE` first | falls back to `HOME`. Data dir is `~/.mori` (platform.rs:52-54) |
| Verbatim path cleanup | platform.rs:59-68 | strips `\\?\` | unchanged |
| venv interpreter | platform.rs:71-77 | `Scripts/python.exe` | `bin/python` |
| System Python launchers | platform.rs:80-90 | `py -3`, `python`, `python3` | `python3`, `python` |
| Foreground window title (call detection) | platform.rs:95-121 | `windows-sys` `GetForegroundWindow` / `GetWindowTextW` | returns empty string (platform.rs:118-121) |

One more OS switch lives outside platform.rs: "reveal in file manager" picks `explorer` / `open` / `xdg-open` (maintenance.rs:231-237). macOS is already handled there.

**Windows-only or Windows-flavoured, not (fully) abstracted:**

1. `app/src-tauri/Cargo.toml:33-34`: `[target.'cfg(windows)'.dependencies] windows-sys`. Correctly gated. Nothing else gated.
2. `app/src-tauri/src/main.rs:1`: `windows_subsystem = "windows"` behind `cfg_attr(not(debug_assertions), ...)`. Harmless on macOS (the attribute only affects Windows).
3. **Tray**: uses Tauri's cross-platform `TrayIconBuilder` (companion.rs:38, 184-220), feature `tray-icon` (Cargo.toml:18). Text says "barra di Windows" (companion.rs:4) but the code is portable. No `icon_as_template` call anywhere (I grepped `src-tauri/src`; none), so I believe a colour icon will show in the macOS menu bar and not adapt to dark/light menu bars. Not verified on a Mac.
4. **Global shortcut default**: `Ctrl+Shift+R` hard-coded twice: `companion.rs:45` and `app/src/companion.ts:15`. Also passed as the tray menu accelerator (companion.rs:148). On macOS this registers the literal Control key. Not wrong, but not Mac-native (Cmd). `app/src/ui/keys.ts:20` maps `commandorcontrol`/`cmdorctrl`/`control` to the label "Ctrl" for every OS.
5. **Pill window** (always-on-top status box): `decorations(false).transparent(true).always_on_top(true).skip_taskbar(true)` (companion.rs:385-396). On macOS Tauri's `transparent` needs `app.macOSPrivateApi: true`; the config description says "Enables the transparent background API" ([Tauri config reference](https://v2.tauri.app/reference/config/), fetched). `tauri.conf.json` has no `macOSPrivateApi` (read, whole file, 46 lines). I believe the pill will have an opaque background on macOS. Not verified on a Mac. The corner placement comment says "dove Windows tiene gia gli stati" (companion.rs:425) and the bottom-centre placement says "sopra la barra delle applicazioni" (companion.rs:437): logic uses `monitor.work_area()` (companion.rs:429), which is cross-platform, but the positions are Windows taskbar assumptions.
6. **Quit guard**: `request_quit` (companion.rs:280-292) is wired to the tray "Esci" item and the window X (companion.rs:194, 236-241). I grepped for `RunEvent`, `ExitRequested`: none (measured, only `app.exit` at companion.rs:283, 290, 557). I believe Cmd+Q on macOS (the default app menu Quit) would bypass the guard and orphan `record.py` during a recording. Not verified on a Mac.
7. **Python discovery** (lib.rs:92-125): probes `<app>/.venv`, `~/.mori/venv`, then `platform::system_pythons()`, running `import soundcard, numpy` (lib.rs:114). On macOS: `venv/bin/python` is handled (platform.rs:75). Gaps: a Finder-launched .app has a minimal PATH, so I believe Homebrew `python3` (`/opt/homebrew/bin`) is not found; and `/usr/bin/python3` on a Mac without Xcode tools is an Apple stub that can pop an "install developer tools" dialog. Both are inference, not verified.
8. **Python scripts are not bundled as a runtime**: `tauri.conf.json:34-37` ships only `scripts/*.py` and `requirements.txt` as resources. No Python, no venv. README:74-80 says "no installer yet, you run from source" (README:42).
9. **`app/scripts/record.py`** (263 lines), exactly which calls:
   - `import soundcard as sc` (record.py:40).
   - Mic: `sc.default_microphone()` (record.py:189).
   - System audio: `sc.default_speaker()` then `sc.get_microphone(id=str(spk.name), include_loopback=True)` (record.py:191-193). This is the WASAPI loopback trick: a loopback "microphone" looked up by the speaker's name.
   - Recorder: `dev.recorder(samplerate=SR, blocksize=...)`, `rec.__enter__()`, `rec.record(numframes=...)` (record.py:75-76, 92). Large device buffer (2 s, 1 s, 0.5 s, default) is tuned for WASAPI: docstring record.py:14-24 ("WASAPI had overwritten capture buffer").
   - Priority boosts use `ctypes.windll.kernel32` (record.py:50-65). On macOS `ctypes.windll` does not exist, raises AttributeError, and the code catches `except Exception: pass`. So it is safe, and does nothing (read).
   - Everything else (writer thread, `.silence`, `.levels`, `.started`, `.done`, mixing to 16 kHz mono) is OS-neutral numpy and file I/O.
10. **Other Python scripts**: `whisper_common.py:35` uses `device="cpu", compute_type="int8"`: neutral. `transcribe_cloud.py`, `embed.py`, `toflac.py` (uses `av`) have no Windows-specific calls (I grepped for `windll|winreg|.exe|sys.platform|os.name|psutil|cuda`: only record.py hits, measured).

| Pill | **Probably opaque / mispositioned (I believe)** | A.1 #5. |

| `pip install -r requirements.txt` | **Works (measured on PyPI JSON)**: ctranslate2 4.8.2 has macOS wheels (cp310 to cp314, arm64 and x86_64, 14 files); `onnxruntime` 1.30.0 has `macosx_14_0_arm64` wheels only; `av` 19.0.1 has macOS wheels; `faster-whisper` 1.2.1 and `fastembed` 0.8.1 are pure Python (no mac wheel needed); `soundcard` 0.4.6 is pure Python. **Intel Mac:** last onnxruntime release with a macOS x86_64 wheel is 1.23.2 (measured); fastembed 0.8.1 requires `onnxruntime>=1.24.2` on Python 3.14 (PyPI `requires_dist`), so Intel + Python 3.14 cannot install. |

| **System audio (the other side of the call)** | **FAILS** | `include_loopback=True` is unsupported in the CoreAudio backend. On macOS `get_microphone(id=speaker_name, include_loopback=True)` then does a plain microphone match (`_match_device`, coreaudio.py:85-105: exact id, substring, then fuzzy regex). Two outcomes: (a) no mic has the speaker's name, `IndexError("no device with id ...")`, caught by `rec_loop` (record.py:100-101), the `sys` channel stays empty, `errs` gets the message, the app shows "I can't hear the other side" style warnings; the mic channel still records. (b) **I believe** if the default output is a headset whose input has the same name (e.g. AirPods), the substring match picks the headset **microphone**, so the "others" channel silently records your own voice a second time. That would label your voice as "Interlocutore". Not verified; needs a tester with a headset. |
| Transcription (local) | **Works, CPU only (I believe)** | `device="cpu", compute_type="int8"` (whisper_common.py:35). CTranslate2 mac arm64 wheels are built with Apple Accelerate + Ruy (see B.4). |
| Transcription (Groq cloud, default) | **Works (I believe)** | Pure `urllib` + `av` FLAC encode (transcribe_cloud.py:21, 108-113). |
| Organize / LLM / recall (embeddings) | **Works on Apple Silicon (I believe)** | JS/SQLite + fastembed on onnxruntime arm64 wheel. Intel Mac: see wheel note above. |
| Call-detect banner | **Never appears** | platform.rs:118-121. |
| Reveal folder | **Works** | `open` (maintenance.rs:233-234). |
| Install for end users | **No installer** | README:42. |

Net: on macOS today you get a recorder with **one channel (mic)**, a working pipeline after it, and a broken "other side". That matches README:40 ("hearing the other side of a call is the missing piece").

## PART B: the web

### B.3 System audio capture on macOS for a bot-free recorder

**(a) Python `soundcard`: no.** Source quote above (coreaudio.py:35-37). The README lists "Mac/coreaudio" as supported and only mentions loopback for Windows (README, 2018-07-17 entry). Last release 0.4.6 on 2026-04-12 (PyPI JSON, measured), BSD-3-Clause. The documented workaround is a virtual device (see d).

**(b) ScreenCaptureKit.**
- `SCStreamConfiguration.capturesAudio`: "A stream doesn't capture audio by default. Set this value to true if you require audio capture." Introduced macOS 13.0 ([Apple doc data](https://developer.apple.com/tutorials/data/documentation/screencapturekit/scstreamconfiguration/capturesaudio.json), measured).
- Permission: Screen Recording. Apple's sample says "The first time you run this sample, the system prompts you to grant the app Screen Recording permission. After you grant permission, you need to restart the app to enable capture." ([Apple sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos), data JSON, measured). That sample requires macOS 15.
- Sequoia adds a periodic re-confirmation: "Allow For One Month" prompt, text "...bypass the system private window picker and directly access your screen and audio..." (secondary sources: [9to5Mac](https://9to5mac.com/2024/08/14/macos-sequoia-screen-recording-prompt-monthly/), [TidBITS](https://tidbits.com/2024/08/19/apple-reduces-excessive-sequoia-permission-requests-shifts-to-monthly)). I did not find the Apple primary page for this; treat as secondary.
- Downside for a recorder: a screen-recording prompt for an audio-only product, and a monthly re-prompt.

**(c) Core Audio process taps (the one to use).**
- `AudioHardwareCreateProcessTap` introduced macOS 14.2 ([Apple doc data](https://developer.apple.com/tutorials/data/documentation/coreaudio/audiohardwarecreateprocesstap(_:_:).json), measured). `CATapDescription`: "describes a tap object that contains an input stream... a mix of all of the specified processes' output audio" (Apple doc data; its metadata says macOS 12.0, which looks like a metadata quirk, not verified).
- Apple article ([Capturing system audio with Core Audio taps](https://developer.apple.com/documentation/CoreAudio/capturing-system-audio-with-core-audio-taps), data JSON measured): sample needs macOS 14.2+. Quote: "To capture audio with a tap, you need to include the `NSAudioCaptureUsageDescription` key in your Info.plist file..." and "The first time you start recording from an aggregate device that contains a tap, the system prompts you to grant the app system audio recording permission." Steps: `AudioHardwareCreateProcessTap()` with a `CATapDescription`, then `AudioHardwareCreateAggregateDevice()`, tap UID via `kAudioTapPropertyUID`, add via `kAudioAggregateDevicePropertyTapList`. Screen Recording is not mentioned anywhere in the article.
- [AudioCap](https://github.com/insidegui/AudioCap) (BSD-2-Clause, 514 stars, last push 2025-08-07, measured via GitHub API): "Sample code for recording system audio on macOS 14.4+", "no screen recording involved", and "There's no public API to request audio recording permission or to check if the app has that permission" (README, fetched). So the prompt appears on first record, and a "have I got permission" check needs private TCC API.
- Failure mode: Meetily's code comment says "If permission is denied, the tap will return silence (all zeros)" (`frontend/src-tauri/src/audio/capture/core_audio.rs:61-62`, read). So denial is silent. Mori must detect "sys channel is exactly zero for N seconds at start" and tell the user. (Mori already has a `.levels` contract and "side is dead" warnings, record.py:30-34, so this fits.)

**(d) Virtual devices (BlackHole etc.).** Works on any macOS but the user installs a driver and builds a Multi-Output device by hand. SoundCard's own search results point there (secondary). Not "just works"; rejected as primary path. I did not fetch BlackHole's licence/README (not verified).

**Smallest sound path for Mori (recommendation, my judgement):**

Candidates:
1. *Rust capture module inside the Tauri process.* Duplicates what record.py already owns (mic, levels, silence, 4 h cap, crash-safe PCM files). Larger change, and a crash in audio code kills the whole app.
2. *Small helper binary that prints 16 kHz mono s16le PCM on stdout* (the AudioTee shape), spawned by `record.py` in place of `get_loopback()` on macOS. Python change is small (one more reader thread feeding the existing `sys_q`). Crash isolation is kept (the existing design says "each stream fails independently", record.py:7-9). The helper can be Rust (copy the pattern from anarlog `speaker/macos.rs` and Meetily `core_audio.rs`, both MIT, with attribution) or Swift (pattern from AudioCap BSD-2-Clause and AudioTee, whose licence must be checked).
3. *Python with pyobjc.* `pyobjc-core` 12.2.2 has macOS wheels (PyPI JSON, measured). I did not verify that `pyobjc-framework-CoreAudio` exposes `AudioHardwareCreateProcessTap`, and an IOProc callback written in Python is risky at 16k realtime. Not recommended, **not verified**.

Pick **option 2 with a Rust helper** (`mori-sysaudio`, a second small `[[bin]]` in `src-tauri`, using `cidre`; fall back to `cpal` loopback if cidre gives trouble). Reasons: same toolchain the maintainer already uses; CI on a macOS runner can compile it without a Mac in hand; two MIT apps with 9.4k and 31.5k stars ship the same call sequence. The Swift alternative is equally small but adds a second toolchain. Keep `soundcard` for the **mic** on macOS (it has a CoreAudio backend).

### B.4 Whisper / embeddings on Apple Silicon

- **faster-whisper + CTranslate2: supported, CPU only.** CTranslate2 `docs/hardware_support.md` (prebuilt binaries): CPU = "x86-64 processors supporting at least SSE 4.1" and "AArch64/ARM64 processors"; GPU = "NVIDIA GPUs with a Compute Capability greater or equal to 3.5". No Metal, no Apple GPU, no ANE (raw file, read). README: backends include "Apple Accelerate" ([CTranslate2 README](https://github.com/OpenNMT/CTranslate2), line 30). The macOS arm64 wheel build script sets `-DWITH_ACCELERATE=ON -DWITH_MKL=OFF -DOPENMP_RUNTIME=NONE -DWITH_RUY=ON` (`python/tools/prepare_build_environment_macos.sh`, read). So: arm64 wheel = CPU with Accelerate + Ruy, no GPU. CTranslate2 4.8.2 (2026-08-31, MIT) has 14 macOS wheels. faster-whisper (MIT) 1.2.1, `requires_python>=3.9`. faster-whisper's README says nothing about macOS/Metal (fetched; **not verified** beyond that). Whether int8 speed on M-series is acceptable: **not measured**; the default Mori path is Groq cloud (README:`transcribes ... by default ... Groq`), local is the fallback.
- **Alternatives that use the Apple GPU / Neural Engine:**
  - whisper.cpp (https://github.com/ggml-org/whisper.cpp, MIT, 54,190 stars, pushed 2026-10-06): README line 18 "Apple Silicon first-class citizen - optimized via ARM NEON, Accelerate framework, Metal and Core ML"; line 59 "On Apple Silicon, the inference runs fully on the GPU via Metal"; line 180 Core ML runs the encoder on the Neural Engine, "more than x3 faster compared with CPU-only" (read).
  - WhisperKit (https://github.com/argmaxinc/argmax-oss-swift, MIT, 6,392 stars, pushed 2026-10-07): "On-device Speech AI for Apple Silicon". Swift; would be a second helper.
  - mlx-whisper (PyPI 0.4.3, MIT, 2025-08-29) on top of MLX (https://github.com/ml-explore/mlx, MIT, 28,677 stars). Python, Apple Silicon only. PyPI shows 0 mac wheels for mlx-whisper itself (pure Python; MLX wheels not checked).
  - The Rust bindings `tazz4843/whisper-rs` show `archived: true` on GitHub (Unlicense, last push 2025-07-30, measured). Do not build on it without checking where development moved (**not verified**).
- **fastembed / onnxruntime**: fastembed 0.8.1 (Apache-2.0, pure Python, 2026-09-22). onnxruntime 1.30.0 (MIT) ships macOS **arm64 only** wheels (`macosx_14_0_arm64`, cp311 to cp314). Intel macOS: last version with an x86_64/universal2 mac wheel is 1.23.2 (2025-10-27). All measured from PyPI JSON. Practical rule: **support Apple Silicon first; Intel Mac is a later, optional target.**

### B.5 Building, signing, notarizing without owning a Mac

- **GitHub macOS runners are free for public repos.** "The use of standard GitHub-hosted runners is free: In public repositories." ([GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions), fetched). Labels (runner-images README, measured): `macos-latest` = macOS 26 arm64; `macos-15` arm64; Intel = `macos-15-intel` / `macos-26-intel`. Public-repo spec: arm64 3 cores / 7 GB, Intel 4 cores / 14 GB ([GitHub runners doc](https://docs.github.com/en/actions/reference/runners/github-hosted-runners), fetched via summariser; moderately reliable). Private-repo macOS price quoted by the doc: $0.062 per minute.
- **tauri-action**: https://github.com/tauri-apps/tauri-action (MIT, 1,618 stars, pushed 2026-10-05). Tauri's pipeline doc matrix: `macos-latest` with `--target aarch64-apple-darwin` and `--target x86_64-apple-darwin`, `windows-latest`, ubuntu; `GITHUB_TOKEN`; `releaseDraft: true` ([Tauri GitHub pipeline](https://v2.tauri.app/distribute/pipelines/github/)).
- **Unsigned / ad-hoc on first launch.**
  - Tauri's doc: "Code signing is required on macOS ... to prevent a warning that your application is broken and can not be started, when downloaded from the browser." Ad-hoc: set `"signingIdentity": "-"`. Apple's own page did not mention Control-click (fetched), consistent with its removal.

I did not find an Apple primary page. **Not verified.** Note that `xattr -cr` is a terminal command: a hard ask for non-technical users.
- **Developer ID + notarization.**
  - Apple Developer Program: $99 USD per membership year; individuals can enrol with a legal name and 2FA; "Prices may vary by region" ([Apple enrolment](https://developer.apple.com/programs/enroll/), fetched). I could not see the euro price. Notarization and Developer ID are not in the free tier ([Apple membership comparison](https://developer.apple.com/support/compare-memberships/), fetched).

Linux, Windows, and macOS") suggests it can be done from Windows. **Whether the full CSR to p12 path works from Windows: not verified.** Cheapest safe plan: the colleague with a Mac does that one step once (about 15 minutes) and the maintainer stores the secrets.

  - Unsigned exe: SmartScreen shows "Windows protected your PC", user must choose "Run anyway"; with no signature, reputation restarts on every new version. Signed with OV or EV certificate also warns at first until reputation builds ("several weeks and hundreds of clean installs"); EV "no longer bypass SmartScreen" ([Microsoft SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation), fetched). The same page says Smart App Control on Windows 11 "will block execution of unsigned files unless the file has a positive reputation".
  - **Azure Artifact Signing** (formerly Trusted Signing): "Starts at $9.99/month" (same Microsoft page). Eligibility from the [quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart): "Public Trust certificates are available to organizations in the United States, Canada, the European Union, the United Kingdom, Australia, New Zealand, Japan, South Korea, Singapore, Switzerland, Norway, and Israel. **Individual developers must be located in the United States or Canada.**" (fetched raw HTML, measured). Needs a paid Azure subscription, not a free or trial one ([FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq)). **So an individual in Italy is not eligible; an organization in Italy (EU) is.**

### B.6 Shipping Python to end users (Windows and macOS)

- **Tauri sidecar mechanism**: `bundle.externalBin`; each binary needs a `-<target-triple>` suffix (e.g. `my-sidecar-aarch64-apple-darwin`, `...-x86_64-pc-windows-msvc.exe`); find the triple with `rustc --print host-tuple`. Doc names the use case: "Python CLI applications or API servers bundled using pyinstaller" so users need not install Python ([Tauri sidecar doc](https://v2.tauri.app/develop/sidecar/), fetched).
- **Option 1: PyInstaller sidecar.** Real example: `vasu-devs/JustHireMe` (AGPL-3.0, 2,257 stars, pushed 2026-09-30; read): `src-tauri/tauri.conf.json` has `externalBin: ["resources/backend/jhm-sidecar-next"]` (line ~29-31), spec file `backend/backend.spec`, separate `backend-macos` job on `macos-latest` and `windows-latest` jobs in `.github/workflows/release.yml:242-245, 171`, ad-hoc `signingIdentity: "-"` (conf line ~54). Cost for Mori: Mori's stack is faster-whisper + ctranslate2 + onnxruntime + av + numpy; freezing native libs with PyInstaller needs hidden-import/data tuning per OS. **I believe** that is fragile and the maintainer cannot debug the mac side. Size of the frozen bundle: **not measured**.
- **Option 2: ship `uv`, create the venv on first run.** `uv` (https://github.com/astral-sh/uv, Apache-2.0 per GitHub API, 90,467 stars) downloads its Python from python-build-standalone (https://github.com/astral-sh/python-build-standalone, MPL-2.0, 4,475 stars): "When uv runs `uv python install`, the binary it downloads comes from python-build-standalone" ([pydevtools handbook](https://pydevtools.com/handbook/reference/python-build-standalone/), search snippet). Real example: `ai4s-research/open-science` (MIT, 1,757 stars, pushed 2026-10-05): `apps/desktop/src-tauri/tauri.conf.json:37-42` lists `externalBin: binaries/opencode, binaries/uv, ...`; its CI step "Fetch bundled uv sidecar" (`build.yml:88`); README line 187 "managed Jupyter environment via bundled `uv`". It ships on macOS 13+ (`tauri.conf.json:46`) and Windows, signed and notarized (build.yml:145-150).
  **Fit with Mori:** `python_cmd()` already prefers `~/.mori/venv` (lib.rs:101-103) and probes it with `import soundcard, numpy` (lib.rs:114). So a first-run step of `uv venv ~/.mori/venv --python 3.12` plus `uv pip install -r requirements.txt` plugs in without changing the script-launch code. Needs network once (Python ~ tens of MB plus wheels; **sizes not measured**), which matches Mori's existing one-time model download.
- **Recommendation:** Option 2 on both OSes (one code path, no freezing, the maintainer can test it on Windows, and a macOS CI job can run the same bootstrap headless). Keep PyInstaller as a fallback only.

## RECOMMENDED ARCHITECTURE FOR macOS

1. **Keep the Python recorder contract** (`.started`, `.levels`, `.silence`, `.done`, two channel WAVs) untouched. Add one platform branch in `record.py`: on `sys.platform == "darwin"`, the `sys` channel reads PCM from a helper process instead of `soundcard` loopback, and `include_loopback` is never called (removes the "microphone with the same name" hazard in A.2).
2. **New helper `mori-sysaudio`** (Rust, `cidre` Core Audio tap, global mono tap, aggregate device, 16 kHz mono s16le to stdout, logs to stderr, exits when stdin closes). Shipped as a Tauri `externalBin` per target triple. Needs macOS 14.2+ (Apple doc). Pattern sources: anarlog `speaker/macos.rs` and Meetily `capture/core_audio.rs` (MIT).
3. **Permissions**: `src-tauri/Info.plist` with `NSMicrophoneUsageDescription` and `NSAudioCaptureUsageDescription` (no screen-recording string needed for taps); hardened runtime + `com.apple.security.device.audio-input` entitlement (as anarlog's Entitlements.plist does, line 5) when signing for real. First-run onboarding step that triggers the mic and system-audio prompts on purpose and verifies with a 3 second test (silence from the tap = permission denied, per Meetily's comment).
4. **UI/OS polish in `platform`-style single place**: a `platform` value from Rust or `navigator.userAgent`; default hotkey `CommandOrControl+Shift+R`; labels "Ctrl" to "Cmd"/"Ctrl" through `hotkeyParts` and one helper for the 35 strings; replace "Windows"/"PC" wording with "this computer" (110 lines to review); `app.macOSPrivateApi: true` for the transparent pill; template tray icon; handle Cmd+Q through a `RunEvent::ExitRequested` guard.
5. **Call detection on macOS**: window titles of other apps need Screen Recording (`kCGWindowName` is only populated with that privilege, [Apple Developer Forums 839069](https://developer.apple.com/forums/thread/839069), search snippet, not opened). `NSWorkspace.frontmostApplication` exists since macOS 10.7 ([Apple doc data](https://developer.apple.com/tutorials/data/documentation/appkit/nsworkspace/frontmostapplication.json), measured) and gives the app name; I believe it needs no permission (not verified). That detects Zoom/Teams/Webex apps but not Google Meet in a browser. Recommendation: ship macOS without Meet detection first; do not add a Screen Recording prompt for a convenience banner.
6. **Python**: bundled `uv` + first-run venv in `~/.mori/venv` (both OSes).
7. **Distribution**: tauri-action matrix on GitHub-hosted runners (free, public repo). Start with ad-hoc signed arm64 DMG + clear "Open Anyway" instructions in the README; move to Developer ID + notarization with API key when the $99 membership is bought.
8. **Scope**: Apple Silicon, macOS 14.2+ (tap API). Intel Macs and macOS 13 (ScreenCaptureKit audio, Screen Recording prompt) out of scope until someone asks.

## THE 3 BIGGEST RISKS

1. **Permissions (TCC) through a Python child process and an ad-hoc signature.** Mic and system-audio consent are tied to the app bundle, with a chain Mori.app to `record.py` to helper. Apple's engineer says macOS "will follow the chain from child process to parent process to determine process responsibility" and that it works while the parent stays alive ([Apple Developer Forums 805245](https://developer.apple.com/forums/thread/805245), fetched), but it is not a documented contract, and I found no source for the audio-capture permission specifically. A denied tap permission returns silence, not an error (Meetily code comment). **I believe** an ad-hoc-signed app that is rebuilt per release may lose granted permissions on each update (not verified). Mitigation: M3/M4 tests on a fresh account, a first-run self-test, and moving the spawn up (Rust spawns the helper and hands the pipe to Python) if the 3-level chain fails.
2. **Untestable-by-maintainer native code that depends on young or single-author crates.** The core feature (hearing the other side) is Core Audio tap code. `cidre` has 220 stars; `cpal`'s own macOS loopback fixed three serious bugs (UB, UID collisions, silent capture) in the 0.18.0 release only four months ago (CHANGELOG). Every fix is a round trip through the colleague. Mitigation: keep the helper tiny and isolated (stdout PCM), copy the call sequence that two shipping MIT apps use, keep a CLI self-test (`mori-sysaudio --selftest`) the tester can run in one command and paste output, and keep `cpal` as plan B.
3. **Distribution trust and first-run weight.** Without Developer ID, every macOS user must go to Privacy & Security > Open Anyway (Control-click bypass removed in Sequoia), and the Tauri doc itself warns ad-hoc does not avoid that; full fix costs $99/year plus an Account Holder and a one-off Mac step. Windows is the same story in miniature: SmartScreen warns on unsigned, and the cheap official signing service is closed to individuals outside US/Canada; SignPath Foundation needs a released installer first. On top, the `uv` first-run downloads Python and about five native wheels (sizes not measured) before the first call can be recorded: a bad first impression if it fails on a slow or filtered network. Mitigation: progress UI with retry, README with screenshots of the "Open Anyway" path, and a decision on the $99 early.
